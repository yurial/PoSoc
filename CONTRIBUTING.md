# Contributing to PoSoc

Спасибо за интерес к проекту PoSoc (Proof of Social) — спецификации децентрализованной сети доверия.

## Структура репозитория

- `specs/` — спецификация протокола, разбитая на два каталога (маска `NN_name.md`): `specs/concept/` — базовые принципы, алгоритмы, математика; `specs/implementation/` — детали реализации (форматы записей, канонизация, криптография). Нормативный документ и единственный источник истины по поведению протокола. Оглавление — `specs/index.md`; глоссарий — `specs/glossary.md` (вне маски NN_name.md).
- `LICENSE` — условия использования.

## Как вносить изменения

### 1. Изменения спецификации

Спецификация нормативна: любое изменение семантики протокола (записи, revoke-семантика, пороги, параметры, гарантии/негарантии) вносится **только** в соответствующие файлы `specs/concept/` и `specs/implementation/` (по одному файлу на раздел, см. `specs/index.md`). Изменения принципов/алгоритмов/математики — в `concept/`; изменения форматов записей, канонизации, криптографии — в `implementation/`.

**Все файлы спецификации должны всегда поддерживаться в актуальном состоянии.** Изменение, затрагивающее несколько разделов или оба каталога, обязано обновлять все затронутые файлы в одном PR — рассинхронизация недопустима.

- Перед изменением откройте issue с описанием проблемы, которую решает правка.
- Изменения семантики (§2–§7) и параметров (§9) требуют обоснования: модель угроз (§1.3), стоимость атаки, совместимость с инвариантами.
- При изменении терминов обновляйте GLOSSARY (`specs/glossary.md`) — определения должны оставаться согласованными с текстом.
- При изменении параметров (§9) проверьте согласованность примеров и справочных таблиц порогов в том же разделе.
- При изменении списка разделов (новый/переименованный файл) обновляйте `specs/index.md` в том же изменении.
- Версию спецификации в `specs/00_intro.md` и `specs/index.md` повышайте при смысловых изменениях; опишите изменение в начале commit message.

### 2. Стиль

- Язык спецификации — русский; термины, имена записей (`LINK`, `VOUCH`, `DECLARE_REVOKE` и т.п.) — на английском.
- Математические формулы — LaTeX-нотация (`$...$`, `$$...$$`).
- Нумерация разделов стабильна: ссылки вида `§3.2.4` используются по всему тексту — не перенумеровывайте существующие разделы без необходимости; новые пункты добавляйте в конец списка.
- Каждое изменение согласуйте с принципами §1.2 и моделью угроз §1.3: если правка расширяет или сужает гарантии — явно отразите это в §1.3.

### 3. Процесс

1. Fork / ветка от `main`.
2. Внесите изменения в соответствующие файлы `specs/` (все затронутые разделы — в одном PR).
3. Проверьте внутреннюю согласованность: перекрёстные ссылки `§x.y`, GLOSSARY (`specs/glossary.md`), таблицу параметров (`09_parameters.md`), примеры, актуальность `specs/index.md`.
4. Откройте Pull Request с описанием: мотивация, затронутые разделы, влияние на гарантии.

### 4. Что не принимается

- Реализации, клиентский код, транспортная инженерия — вне скоупа репозитория (§2.2.4, §8.6, §12): спецификация нормативна, реализации — отдельный артефакт.
- Изменения, смягчающие гарантии без явного анализа стоимости атаки.
