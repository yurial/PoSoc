# Спецификация протокола PoSoc (v0.10)

## 1. Назначение, принципы, модель угроз

### 1.1 Назначение

Цель — децентрализованная сеть доверия (**PoSoc — Proof of Social**), позволяющая каждому участнику отличать реальных людей от ботов/виртуальных аккаунтов **в пределах наблюдаемого им компонента социального графа**. Гарантии — условные и вероятностные, в терминах стоимости атаки.

### 1.2 Принципы

1. **Отсутствие инфраструктуры.** Нет корневых узлов, валидаторов, ledger, субстрата упорядочивания. Сеть — участники и их связи.
2. **Одноранговость.** Полномочий нет; каждый валидирует состояние сам.
3. **Субъективное локальное доверие.** Участник доверяет иерархиям, достижимым из его L0 (§6).
4. **Стоимость вместо альтруизма.** Протокол не предполагает честности: подтверждение ботов — стоимостно и рекуррентно. Подкуп и обман — векторы стоимости (§1.3).
5. **Публичность внутри компонента.** Записи публичны в компоненте связности; валидность — чистая функция данных.
6. **Эфемерность.** Все факты — автопродлеваемые TTL-объекты с мгновенным revoke; «купленного» факта не существует.
7. **Взаимность согласия.** Вход двусторонен (обе подписи / quorum); revoke и выход — односторонни. Молчаливого согласия нет.
8. **Эмерджентность иерархии.** Edges и levels — выводимое состояние, не записи.
9. **Время подписи.** Состояние — функция множества подписанных записей и текущего времени; порядок доставки семантики не имеет.
10. **Единая семантика revoke.** Каждый consent object X отзывается действием `X_REVOKE` того же подписанта; свежая подпись всегда сильнее старой.

### 1.3 Модель угроз

**Противник может:** создавать неограниченно ключей (Sybil); контролировать связи своих узлов; создавать группы и declarations (permissionless); получать связи с людьми (встреча, обман, подкуп); похищать ключи; бэйдейтить $t_{sign}$ собственных записей; задерживать/утаивать записи при ретрансляции; смещать собственные часы.

**Противник не может (криптографически):** подделать подпись; создать/продлить consent object без требуемых подписей; включить участника в L0 без его подписи; отозвать чужой consent object; аннулировать poison mark без подписи создавшей стороны или fresh LINK пары; привязать группу к иерархии без живых внешних связей и quorum declarations.

**Гарантии (в пределах допущений):**
- *Inclusion cost:* включение бот-компонента в человеческую иерархию требует $\approx t$ взаимных живых связей; линейно по порогу, рекуррентно ($\le T_{life}$).
- *Isolation:* declarations без внешних живых связей не создают edges (disjoint count, §5.4); транспортная изоляция дублирует структурную (§2.2).
- *Backdating containment:* поддельный revoke живёт до момента counter-revoke; свежая подпись жертвы всегда сильнее (§3.2).
- *Hijack localization:* окна сжимаются в $1+N$ раз; чужие marks угонщик не стирает; исключение — quorum отзывов, мгновенно.

**Негарантии:** многоличность (§10.2); сговор выше порогов (§10.5); приватность (§11); мгновенная глобальная согласованность (§2.5); гарантированная доставка (§10.9–10.10).

## 2. Архитектура

### 2.1 Identity

1. Личность — пара ключей $(x, pk)$, Ed25519 (§8). Секрет не публикуется.
2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.
3. Один человек может владеть несколькими ключами (§10.2); перенос истории протоколом не гарантируется (§7.3.3).

### 2.2 Сеть без ledger

**Объекты узла:** БД состояния (живые записи + ретроспективный буфер), sync queue.

1. **Транспорт = социальный граф.** Запись ретранслируется только узлам с активной LINK. Компонент связности — изолированная вселенная данных: записи человеческого компонента физически не достигают бот-кластеров (двойная изоляция). Свежий ключ без связей не получает трафика; установление LINK включает слив состояния.
2. **Обработка записи:** проверка (подписи, каноническая форма, применимость, §2.4.8) → применение к БД → постановка в sync queue → рассылка соседям.
3. **Anti-entropy.** Периодическая сверка множеств записей с каждым соседом (реконсиляция по диапазонам времени и хешам); расхождения подтягиваются. Утаивание записей соседом обнаруживается сверкой через других соседей; риск единственного моста — §10.9.
4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).
5. **GC horizons (минимум для корректности собственного состояния):** записи пары — до $t_{last} + 2T_{life}$ ($t_{last}$ — позднейшая $t_{sign}$ пары; лемма §3.4.1); consent objects — до конца эффекта; L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

### 2.3 Записи

Канонический CBOR (§2.7); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke) и **actions** (мгновенный эффект).

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `LINK(u,v)` | обе стороны | object, $T_{life}$ | link instance пары (§3) |
| `LINK_REVOKE(u→v, memo?)` | $u$ | action | terminирует instance + poison mark (§3.2) |
| `SELF_CONF(P,G)` | $P$ | object, $T_{life}$ | само-подтверждение членства в L0 (§4) |
| `SELF_CONF_REVOKE(P,G)` | $P$ | action | отзыв → выход из L0 (§4.2) |
| `VOUCH(Q,P,G)` | $Q$ | object, $T_{life}$ | поручительство за $P$ (§4) |
| `VOUCH_BATCH(Q,G,[P…])` | $Q$ | object (пакет) | набор vouches (§4) |
| `VOUCH_REVOKE(Q,P,G)` | $Q$ | action | отзыв vouch (§4.2) |
| `DECLARE(P,H)` | $P$ | object, $T_{life}$ | голос в C1-quorum (§5.2) |
| `DECLARE_REVOKE(P,H)` | $P$ | action | отзыв declaration (§5.2) |
| `L0_GENESIS(P, descriptor)` | $P$ | action | адрес L0 (§4.5) |

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

### 2.4 Время, конфликты, revoke-семантика, детерминизм

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.
2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и пере-оценивается при повторной доставке (часы могли догнать). $t_{sign} \in (now,\ now+\Delta]$ — хранится и ретранслируется, к состоянию не применяется до догонa часов.
3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов (§3.4.1).
4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.
5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$: уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$; объекты с большей $t_{sign}$ — свежее согласие, выживают. Специфика `LINK_REVOKE` (binding, poison) — §3.2.
6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.
7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван (§2.4.5).
8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Транзиторное неравенство хранимых множеств между узлами — норма; сходимость — §2.5. Правила игнорирования (детерминированные): неверная подпись; неканоническая форма; $t_{sign} > now+\Delta$; неприменимость (`LINK_REVOKE` без bound instance — §3.2; revoke объекта, которого нет в БД). Капы §2.6.2 и rate-limit §2.6.3 — правила **отбора и замещения на уровне состояния**, не валидации: «лишние» записи хранятся, но не считаются.
9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `DECLARE` (relevance — политика хранения/ретрансляции, не валидности).

### 2.5 Синхронизация и сходимость

Gossip при появлении записи + anti-entropy по расписанию. Согласованность — в пределе; в моменте — субъективные виды. Потребитель доверия всегда читает текущее состояние. Цензура соседа подавляет доставку, но не искажает семантику: задержанная запись применяется со своей $t_{sign}$.

### 2.6 Antispam (структурный)

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (declarations от ключей вне живых $R_{str}$ не хранятся; re-publish — §2.4.9).
2. **Капы живых объектов на ключ (уровень состояния):** ≤ 16 `SELF_CONF`; ≤ 32 `DECLARE` (сверх — считаются 32 с наибольшими $t_{sign}$, тай-брейк по $H$); `VOUCH` считается только от активных членов (правило подсчёта: vouch от не-члена хранится, не считается); `LINK` капом не ограничен (стоимость встроена в подпись контрагента).
3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.

### 2.7 Канонизация

Канонический CBOR (ключи отсортированы); пары ключей лексикографически; самосвязи запрещены; $H$ — BLAKE3; округления порогов — $\lfloor x + 10^{-9} \rfloor$.

### 2.8 Record formats (норматив)

Record = `{type, t_sign, payload, sigs}`; sigs — массив `{pk, sig}`, **отсортированный по pk**. Signing payload = канонический CBOR `{type, t_sign, payload}` — каждый подписант подписывает одни и те же байты. Идентичность записи = $H(\mathrm{record})$ (полные канонические байты); дедупликация по содержимому.

| type | payload | sigs |
|---|---|---|
| `LINK` | `{u: pk, v: pk}` ($u < v$) | `[u, v]` |
| `LINK_REVOKE` | `{from: pk, to: pk, memo?: bstr ≤ 256}` | `[from]` |
| `SELF_CONF` / `SELF_CONF_REVOKE` | `{group: ID_G, member: pk}` | `[member]` |
| `VOUCH` / `VOUCH_REVOKE` | `{group: ID_G, voucher: pk, member: pk}` | `[voucher]` |
| `VOUCH_BATCH` | `{group: ID_G, voucher: pk, members: [pk; ≤30]}` | `[voucher]` |
| `DECLARE` / `DECLARE_REVOKE` | `{group: ID_H, declarant: pk}` | `[declarant]` |
| `L0_GENESIS` | `{descriptor: tstr ≤ 128, initiator: pk}` | `[initiator]` |

Идентификаторы: $ID_G = H(\texttt{"L0"} \Vert \text{descriptor} \Vert pk_{initiator} \Vert t_{sign})$; $ID_H = H(\texttt{"GROUP"} \Vert \text{descriptor} \Vert pk_{founder})$, founder — pk первой (по $t_{sign}$) `DECLARE` (техническая роль без привилегий). Доменное разделение BLAKE3 — по тегам типов; tie-break $H(\mathrm{record})$ — от полных канонических байтов.

## 3. Связи

### 3.1 Instances

1. Связь — отношение пары ключей; не более одного текущего instance.
2. `LINK(u,v)` с $t_c = t_{sign}$ создаёт instance; instance с большей $t_c$ замещает прежний (архив); метки пары усекаются (§3.2.4).
3. Активная связь на $\tau$: instance не терминирован и не распался.

### 3.2 `LINK_REVOKE` и poison mark

**Реконструкция пары $(u,v)$:**

1. **Instances:** записи `LINK` упорядочиваются по $t_c$ (тай-брейк — меньший $H$).
2. **Binding:** `LINK_REVOKE(u→v)` с $t_{sign}=s$ привязывается к instance $\ell$ = последнему `LINK` пары с $t_c \le s$. Такого нет — запись игнорируется.
3. **Разрешение по направлениям.** Записи направлений $u \to v$ и $v \to u$ **независимы и не конфликтуют** (взаимный revoke законен: каждая сторона отзывает своё согласие). Внутри одного направления, привязанного к $\ell$, действует запись с **максимальным** $t_{sign}$ (тай-брейк — меньший $H$); прочие игнорируются.
4. **Эффект действующего `LINK_REVOKE(u→v, s)`** на instance $\ell$:
   - $t_b = \mathrm{clamp}(s,\ t_c(\ell),\ t_c(\ell)+T_{life}) = \min(s,\ t_c(\ell)+T_{life})$ (binding даёт $s \ge t_c$);
   - $\ell$ **terminируется** в $t_b$ (при нескольких действующих revoke — в наименьшем $t_b$);
   - **poison mark против $v$:** активен на $[\,t_b,\ \min(t_c(\ell)+T_{life},\ t_{relink})\,)$, где $t_{relink}$ — $t_c$ следующего `LINK` пары (нет — $\infty$).
   - При $s > t_c(\ell) + T_{life}$: интервал пуст — terminация без mark.
5. **Counter-revoke.** Свежая запись того же направления (строго больший $t_{sign}$) замещает прежнюю: её mark отменяется. Владелец ключа опровергает подделку в **любой** момент — в том числе после $t_c + T_{life}$ (кламп даёт пустой интервал: подделка стёрта, нового mark нет).

**Свойства:**

1. **Направленность:** mark создаётся против контрагента отзывающего («травится покинутый»). **Взаимные revoke → обе стороны помечены.**
2. **≤ 1 mark на пару-направление, ≤ 2 на пару.** Метки разных пар стекируются; $N_a \le \deg(a)$ — инвариант сохраняется.
3. **Truce.** `LINK(u,v)` усекает метки **обоих направлений** пары; окна выживающих связей $u$ и $v$ расширяются немедленно; метки третьих лиц не затрагиваются.
4. **Отмывание недоступно.** Аннулирование mark требует: fresh `LINK` пары (подписи обеих сторон, включая отзывавшего) **либо** counter-revoke владельцем ключа отзывавшего. Угонщик не стирает метки друзей жертвы.
5. **Цена грифинга.** Цикл `LINK↔LINK_REVOKE` требует подписи «жертвы» на каждый `LINK`; собственные метки пары не накапливаются (≤2).
6. **Каскад revoke** против одного ключа — публичный сигнал компрометации (§7.4).

### 3.3 Decay

$$W_\ell(\tau) = \frac{T_{life}}{1+N_u(\tau)+N_v(\tau)},\qquad d(\ell)=\min\{\tau \ge t_c:\ \tau - t_c \ge W_\ell(\tau)\}$$

1. $W$ кусочно-постоянна; $d(\ell)$ — сканирование моментов начала/конца меток против $u$ и $v$. Распад не позднее $t_c + T_{life}$.
2. Активность $\ell = [t_c,\ \min(d(\ell),\ t_b))$.
3. **Необратимость — относительно текущего множества записей:** расширение окон отодвигает распад выжившего, но не оживляет распавшийся; позднее прибытие записи может переписать историю пары (осознанное следствие «прошлое не ограничено», §2.4.3). Оживление пары — только её новый `LINK`.

### 3.4 Леммы и пример

1. **GC horizon.** Mark не создаёт эффектов позже $t_c(\ell) + 2T_{life}$: сам живёт $\le t_c + T_{life}$ и влияет на окна связей, созданных не позже чем на $T_{life}$ позже.
2. Все производные величины вычисляются из хранимого множества записей без истории применения.

*Пример* ($T_{life}=12$ мес., проверен): revoke $(a,b)$ в $t{=}2$ (instance $t_c{=}0$) → mark $[2,12)$ против $b$; связь $(b,c)$ ($t_c{=}0$): окно 6 мес., распад $t{=}6$; truce `LINK(a,b)` в $t{=}4$ усекает mark → окно $(b,c)$ немедленно 12 мес., распад $t{=}12$ — выжившая связь спасена; $(a,b)$ — свежий instance до $t{=}16$. Взаимный `LINK_REVOKE(b→a)` в $t{=}3$ добавил бы mark против $a$ на $[3, 12)$ — независимо от mark против $b$.

## 4. Базовые группы (L0)

### 4.1 Принцип

L0 — реальные малые группы. Membership — **непрерывный двусторонний предикат**: self-подтверждение ∧ поручительства группы ∧ link-опора. Ни ростер, ни запись не включают $P$ без подписи $P$; пребывание — при поддержке большинства. Вход двусторонен; revoke и выход — односторонни.

### 4.2 Объекты

- **`SELF_CONF(P,G)`** — «я в G» (TTL, продлевается клиентом $P$).
- **`VOUCH(Q,P,G)`** — «P — наш» (TTL, продлевается клиентом $Q$; пакетируется `VOUCH_BATCH`).
- **`SELF_CONF_REVOKE(P,G)`** — отзыв self-подтверждения: membership $P$ прекращается немедленно, односторонне (выход).
- **`VOUCH_REVOKE(Q,P,G)`** — отзыв vouch; **quorum отзывов** роняет поддержку немедленно — это и есть исключение (события EXPEL не существует; batch отзывов — симметрично batch vouches).

### 4.3 Roster computation (growth priority)

Membership = **выход детерминированного алгоритма** на $\tau$:

1. **Candidates:** все $P$ с живой `SELF_CONF(P,G)`.
2. **Cap-30 (до раундов):** при $>30$ кандидатов берутся 30: (i) по числу живых `VOUCH` от других кандидатов (убыв.); (ii) при равенстве — fresher $t_{sign}$ `SELF_CONF`; (iii) при равенстве — $pk$ (возр.). Непопавшие остаются кандидатами (записи не теряются, re-publish не нужен).
3. **Growth priority:** начальный roster = **все** отобранные кандидаты. Присоединение никогда не блокируется маргинальностью incumbents: если укрупнённые пороги инвалидируют incumbents — они удаляются раундами (**squeeze-out** — принятая семантика, §10.16).
4. **Synchronous rounds:** на каждом раунде **одновременно** удаляются все, нарушающие относительно текущего roster:
   (a) **vouch-quorum:** живых `VOUCH` от текущих членов ≥ $\lfloor |M|/2 \rfloor + 1$;
   (b) **cohesion:** активных связей с текущими членами ≥ $\lfloor |M|/2 \rfloor + 1$.
   Итерация до стабилизации. Результат **sound** (инварианты выполнены); **maximality не гарантируется** и не заявляется. Вычисление детерминировано.
5. **Freshness tie-break:** любые равные притязания в L0-вычислениях (cap, равные счёты) → fresher $t_{sign}$, затем $pk$.
6. **Quench:** $|M_{act}| < 4$ → roster пуст; edges от группы отваливаются мгновенным каскадом (§5.6).

### 4.4 Динамика: две скорости

- **Явные действия — мгновенны:** `SELF_CONF_REVOKE` (выход), quorum `VOUCH_REVOKE` (исключение), потеря cohesion (удаление раундом при следующем пересчёте).
- **Угасание — ≤ $T_{life}$:** expire без продления покрывает мёртвые узлы.
- **Вступление/возвращение:** материализация = живая `SELF_CONF` + набор vouches; после угасания поддержки — только заново набранный quorum. В норме продление тихое.
- Roster мгновенно входит в $R_{str}$ → пороги → edges (§5.6).

### 4.5 Genesis

`L0_GENESIS(initiator, descriptor, t_sign)` задаёт адрес $ID_G$ (§2.8) — без привилегий. Группа жива, когда ≥ 4 участников удовлетворяют §4.3 (их `SELF_CONF` и взаимные vouches — обычные объекты). Церемоний нет: genesis — адрес, остальное — непрерывный предикат.

## 5. Эмерджентная иерархия

### 5.1 Принцип

Явные акты — связи, membership в L0, declarations. Edges, levels, валидность — выводимое состояние, перевычисляемое непрерывно.

### 5.2 Declarations

1. **`DECLARE(P,H)`** — подписанное $P$ утверждение «поддерживаю принадлежность сообществ, где я состою, к $H$»: голос в C1-quorum **каждого** $X$ с $P \in R_{str}(X)$. TTL $T_{life}$, тихо автопродлевается (rate-limit §2.6.3). Одна declaration голосует во всех соответствующих quorum — один человек, одно согласие; disjoint count по уникальным pk исключает двойной счёт.
2. **`DECLARE_REVOKE(P,H)`** — мгновенный односторонний отзыв (лёгкое возражение): живость declaration обрезается в $t_{sign}$; quorum падает → edge отрывается мгновенно. Осцилляция REVOKE↔DECLARE самонаказуема (отрыв мгновенный, возврат — через $T_{hold}$).
3. **Адрес группы** $ID_H$ (§2.8); имя — не identity (§10.1); identity сообщества — структура.
4. **Isolate** — группа без живых детей: $R_{str} = \varnothing$, адрес не хранится сетью (владелец хранит), бутстрапится (§5.5). Declarations посторонних не хранятся (§2.6.1, §2.4.9).

### 5.3 Rosters

1. $R_{decl}(H)$ — участники с живыми declarations: заявления, **не носители доверия, в порогах не участвуют**.
2. $R_{str}(H) = \bigcup_{C \in \mathrm{children}(H)} R_{str}(C)$ по уникальным pk; для L0 — активный roster §4; isolate — $\varnothing$.
3. Участник «в иерархии» ⟺ состоит в валидной L0, транзитивно привязанной к доверенному компоненту.
4. Разделение ростеров исключает циркулярность.

### 5.4 Thresholds и disjoint count

1. **Disjoint count:**
$$U_{X \Rightarrow Y} = \big|\{\,p \in R_{str}(X):\ \exists\, q \in R_{str}(Y) \setminus R_{str}(X),\ \text{связь } (p,q) \text{ активна}\,\}\big|$$
2. **Пороги** ($avg = (|X|+|Y|)/2$, $\rho = |big|/|small|$, $f = f(avg)$, $\kappa = \kappa(avg)$):
$$f(m) = \begin{cases} 0.5, & m < 30 \\ 0.05 + 0.45 \cdot 1.5^{-\log_{10}(m/30)}, & 30 \le m \le 10^4 \\ 0.05 + 0.1618 \cdot 4^{-\log_{10}(m/10^4)}, & m > 10^4 \end{cases}$$
$$\gamma(\rho) = \min(1,\ f + c(\rho-1)),\ c = 0.25;\qquad \kappa(m) = \min(\lfloor m/2.5 \rfloor,\ 4500)$$
$$t_{big} = \min\big(|big|,\ \max(\lfloor f \cdot |big| \rfloor,\ \kappa) + 1\big),\qquad t_{small} = \min\big(|small|,\ \max(\lfloor f \cdot |small| \rfloor,\ \lfloor \gamma \cdot |small| \rfloor,\ \kappa) + 1\big)$$
3. **Пара проходит** ⟺ $U_{X \Rightarrow Y} \ge t_X$ ∧ $U_{Y \Rightarrow X} \ge t_Y$.
4. **Инварианты:** (i) при непустых внешних частях и полной взаимной внешней связности пара проходит (при большом пересечении ростеров внешние части малы — оговорка существенна); (ii) $t \le |side|$; (iii) равные пары: $t = \min(m, \max(\lfloor f\,m \rfloor, \kappa(m)) + 1)$; (iv) $\rho{=}1$, $m<30$: $t = \lfloor m/2 \rfloor + 1$; (v) асимметрия — цена до единогласия малой стороны.
5. **Лемма (инъекция одного ключа).** Угнанный аккаунт + 30 сибил-ключей: $U_{X \Rightarrow Y} = 30 \ge t_X$, но $U_{Y \Rightarrow X} = 1 < t_Y$ — двусторонность отбивает инъекцию через один человеческий ключ.

### 5.5 Live edge: условия, активация, bootstrap, freeze

**Статусы групп:** *isolate* (0 живых детей, $R_{str} = \varnothing$, без уровня); *vertex* (≥ 2 живых детей); *free group* (1 живой ребёнок — возникает только понижением vertex; edge грандфатерится; приём детей и привязка вверх — на общих основаниях).

**Edge $X \to H$ жив на $\tau$ ⟺ непрерывно:**

- **C1 (consent):** ≥ $\lfloor |X|/2 \rfloor + 1$ участников $R_{str}(X)$ имеют живые declarations в $H$;
- **C2 (corroboration, all-pairs):** для **каждого** живого ребёнка $Y \in \mathrm{children}(H) \setminus \{X\}$ пара $(X,Y)$ проходит;
- **C3 (acyclicity):** не существует пути $H \Rightarrow^* X$ по живым рёбрам.

**Активация.**

- **Attach к живой группе** (≥ 1 живого ребёнка у $H$; $R_{str}(X) \ne \varnothing$ — иначе C1 невыполним): C1–C3 выполняются непрерывно $T_{hold}$ → активация. Проверка пар кандидата со всеми живыми детьми делает активацию безопасной для них.
- **Freeze ∥ hold window.** Freeze не приостанавливает накопление окна; активация в $\max(\text{конец freeze},\ \text{конец окна})$.
- **Freeze:** $T_f$ от `L0_GENESIS` и от bootstrap-активации вершины; блокирует только **новые** активации рёбер вверх; существующие рёбра и дети не затрагиваются.

**Bootstrap пустой группы $H$:**

1. **Candidates** $K$: группы с живым C1-quorum к $H$.
2. **S-set:** $S \subseteq K$, $|S| \ge 2$, все пары **внутри $S$** проходят. Существование одного $S$ достаточно — кандидаты вне $S$ ничего не блокируют (anti-DoS: сибил без внешних связей не входит ни в одно $S$).
3. **Окно:** для фиксированного $S$ — непрерывное выполнение условий всех его членов $\ge T_{hold}$; изменение состава $S$ (потеря члена, падение пары) перезапускает окно **этого** $S$; события кандидатов вне $S$ окно не перезапускают.
4. **Выбор при активации:** среди $S$ с завершённым окном — inclusion-maximal; при одновременном завершении несравнимых — окно с более ранним стартом; при равенстве — лексикографически наименьший отсортированный список $ID$.
5. **Эффект:** $\mathrm{children}(H) = S$; $R_{str}(H) = \bigcup$; freeze $T_f$ для $H$; прочие кандидаты присоединяются после по общим правилам attach.

Одновременные активации оцениваются в детерминированном порядке — по $(t_{sign},\ H)$ объекта-условия; активированное ребро цикла создать не может (C3).

### 5.6 Динамика: мгновенный пересчёт

1. **Detach — мгновенный.** Провал C1 у edge **или** провал любой пары $(Y_i, Y_j)$ → **оба** edge пары отпадают немедленно; $H$ пересчитывается немедленно.
2. **Понижение.** Живых детей $< 2$: при 1 — vertex → **free group** (edge грандфатерится, $L = 1 + L(\text{ребёнка})$); при 0 — **isolate**, восходящие edges отваливаются **тем же пересчётом** (C1 при пустом $R_{str}$ невыполним). Изолят привязывается **только bootstrap-ом**. Рёбра детей сохраняются; каскад — полный мгновенный пересчёт без искусственных задержек.
3. **Levels:** $L(H) = 1 + \max_C L(C)$; isolate — без уровня; метаданные. Ожидаемая глубина при ширине $\bar k \sim 5\text{–}10$: $D \approx \log_{\bar k}(P/\overline{|L0|}) \approx 7\text{–}10$.
4. **Параллелизм:** multi-parenting — штатное состояние DAG; дети не блокируются ничем, кроме собственного freeze.
5. **Пересчёт:** непрерывный; пороги всегда по текущим структурным численностям (дрейф — §10.11).

### 5.7 Возражения и выход

1. **Лёгкое** — `DECLARE_REVOKE`: quorum C1 падает, edge отрывается мгновенно.
2. **Тяжёлое** — `LINK_REVOKE` (§3.2).
3. **Выход группы из родителя** — массовый `DECLARE_REVOKE` членов $X$; отдельного события нет.

### 5.8 Изоляция ботов

Declarations permissionless, но: quorum L0 контролируются людьми; isolate имеет пустой $R_{str}$; disjoint count исключает co-membership; каждая пара на пути бот-поддерева в человеческую иерархию требует живых человеческих связей с TTL ≤ $T_{life}$. Одиночные edges (free groups) обхода не открывают: соединяющее ребро встречает сестёр (self-healing — оторванное от людей поддерево теряет корроборацию не позже $T_{life}$).

### 5.9 Мотивация связей

Алгоритм не регламентирует, кого подтверждать; предполагается, что реальных связей достаточно для связывания графа.

## 6. Потребление доверия

### 6.1 Proof membership

Доказательство — **поддерево**, не путь: для каждого parent на пути предъявляются все живые дети, их перекрёстные связи (C2), численности $R_{str}$, живые declarations (C1), плюс собственная L0 заявителя (SELF_CONF + vouches + связи). Причина: валидность одного edge — свойство всего множества детей. Сильный режим — верификация по собственной replica (чистая функция состояния). Декларации в доверии не участвуют. Commit-structures (Merkle-корни поддеревьев) для лёгких верификаторов — roadmap (§11).

### 6.2 Субъективная оценка

Доверенное множество — транзитивное замыкание родителей L0 верификатора (+ его политика: размер, возраст, аномалии §7.4). Глобального флага «человек» нет. Практическая картина: люди — гигантский компонент; бот-кластеры — изолированные компоненты (структурно и транспортно).

### 6.3 Spot-check (SHOULD; расшифровка)

**Проблема.** Prover может утаить неблагоприятные записи (`SELF_CONF_REVOKE`, `VOUCH_REVOKE`, `LINK_REVOKE`, распад связей). Верификатор без полной копии не видит неполноту предъявленного множества — это главный вектор обмана лёгкого верификатора.

**Механизм.** Верификатор выбирает $k$ случайных участников из предъявленных rosters и запрашивает у них (транспорт — social graph верификатора / anti-entropy pull к собственной replica) записи, затрагивающие proof: живость SELF_CONF/VOUCH/DECLARE и активность связей поддерева. Расхождение с предъявленным → reject.

**Свойства.** Записи публичны в компоненте: утаивание prover'ом не мешает другим узлам ими владеть; обнаружение утаивания — с вероятностью $\approx 1-(1-p)^k$, где $p$ — доля опрошенных, владеющих противоречащей записью. Запросы liveness — вне гарантий.

**Пределы.** Скоординированное сокрытие целым компонентом; верификатор без независимых путей к данным. Сильный режим (собственная replica) от этих пределов свободен.

**Статус:** SHOULD — политика клиента; на консенсус не влияет.

## 7. Защитные механизмы

### 7.1 Гистерезис и freeze

$T_{hold}$ — окно непрерывного выполнения условий **перед активацией** (уведомления, возражения, дорост связей). Отрыв мгновенный — асимметрия осознана: включение медленное, отторжение немедленное; флаппинг подавляется ценой повторного включения. $T_f$ — анти-накачка и анти-ротация топологии; параллелен hold window.

### 7.2 Decay и poison

Окна $T_{life}/(1+N)$, стекирование по разным парам, конечные метки, truce. Взаимные marks (≤2 на пару) — осознанная цена симметрии revoke: покинутый с обеих сторон получает двойное сжатие только от этой пары; каскад против одного ключа по-прежнему ограничен $\deg$.

### 7.3 Hijack, потеря ключа, боты

1. **Hijack.** Друзья публикуют `LINK_REVOKE` и `VOUCH_REVOKE` (quorum). Окна сжимаются в $1+N$ ($T_{life}{=}12$ мес., $N{=}6$ — изоляция за ≈1.7 мес.); обновления требуют подписей друзей; их marks угонщик не аннулирует (§3.2.4). Угонщик может `DECLARE_REVOKE` — рёбра отвалятся мгновенно; вред обратим. Бэйдейтинг `LINK_REVOKE` от имени жертвы нейтрализуется counter-revoke (§3.2.5) — свежая подпись сильнее.
2. **Честное восстановление.** Переверберация лично → друзья подписывают `LINK` (marks обоих направлений аннулируются, instances чисты) → declarations возобновляются. Без «штрафа переживания».
3. **Потеря ключа (ротация) — рецепт, без специального события:** новый ключ вступает в L0 (SELF_CONF + vouch-quorum) → старый выводится (`SELF_CONF_REVOKE` при контроле или quorum `VOUCH_REVOKE` при утере) → связи переподписываются контрагентами (`LINK` — truce чистит метки пар). Marks не переносятся (привязаны к ключу); вору quorum не собрать; ботам ротация бесполезна. Непрерывность «тот же человек» — негарантия (§10.2).
4. **Боты.** Не проходят порогов без человеческих связей (§5.8).

### 7.4 Обнаружение аномалий (advisory)

Churn (`LINK`/`LINK_REVOKE` циклы, осцилляции); каскадные revoke против одного pk; массовые `LINK` после каскада («прощение-фишинг»); синхронные DECLARE/DECLARE_REVOKE, спам адресов, набеги, namespace-спуфинг; звёздные топологии; распределения степеней/плотности; синхронность операций; динамика L0 (синхронные вступления/отзывы, squeeze-out паттерны, growth-атаки); накачка уровней, цепочки одиночных детей; DAG-специфика (штормы привязок, близнецы-родители); паттерны memo.

## 8. Криптография и объёмы

1. **Подписи:** Ed25519 (pk 32 Б, sig 64 Б); интерфейс допускает постквантовые схемы.
2. **Хеши:** BLAKE3, доменное разделение по типам записей (§2.8).
3. **Канал уведомлений (опционально):** $s_{uv} = \mathrm{HKDF}(\mathrm{X25519}(x_u, pk_v))$ — координация продлений и подписей `LINK`; не источник истины.
4. **Канонизация:** детерминированный CBOR (§2.7–2.8).
5. **Объёмы записей:** `LINK` ≈ 200 Б; одиночные объекты/revoke ≈ 150 Б; `VOUCH_BATCH(30)` ≈ 1 КБ.
6. **Подписная нагрузка на человека в год** (спецификаруемая часть — cadence TTL): ≈ 60 продлений `LINK` + 2 `SELF_CONF` + 2 vouch-пакета + ~$2D \approx 16\text{–}20$ declarations ≈ **80–100 тихих записей/год**. Пропускная способность, политика relay и объём хранилищ — **вне спецификации** (implementation-defined; оценки — в сопроводительных материалах).

## 10. Ограничения и открытые вопросы

1. **Namespace:** имперсонация имён нерешаема; identity — структура.
2. **Многоличность:** принципиально не детектируется; смягчения — стоимость связей, эвристики.
3. **Публичность согласия:** видны составы и declarations; приватизация — §11.
4. **Мажоритарная жёсткость:** индивидуум не привяжется без большинства своей L0.
5. **Сговор выше порогов:** выше $\kappa$ — вне гарантий.
6. **Спам:** структурно ограничен; остаточное — объёмы буферов.
7. **Грифинг ядом:** каскады сжимают окна; взаимные marks (≤2 на пару) усиливают взаимный грифинг пары; ограничители — конечность, truce; остаточный риск признан.
8. **Hijack и клиентские политики:** явные подтверждения операций; предупреждения о контрагентах с историей revoke.
9. **Цензура соседа:** утаивание записей; anti-entropy и multi-parenting смягчают; единственный мост — риск.
10. **Доступность данных:** prover может скрывать записи; spot-check (§6.3) смягчает; скоординированное сокрытие — остаточный риск.
11. **Дрейф порогов при росте:** рост брата повышает парный порог при статичных связях — мгновенный detach и дорогой возврат ($T_{hold}$); живучесть — multi-parenting.
12. **Сложность вывода:** all-pairs — $O(\sum_H k_H^2)$ за пересчёт; обязательны индексы и инкрементальность.
13. **Консервативность rounds:** синхронное удаление — не максимальный roster; осознанно (soundness важнее полноты).
14. **Расхождения часов:** влияют на мгновенные виды, не на сходимость; $\Delta$ покрывает скью.
15. **Управление параметрами:** изменение = форк; governance не специфицирован.
16. **Squeeze-out (growth priority):** присоединение может вытеснить incumbents на пороге вплоть до quench; враждебный join стоит vouch-quorum и разрушает также членство атакующего; осознанная цена детерминизма и отсутствия задержек.
17. **Транспортная инженерия:** relay-политика, пропускная способность, объёмы хранилищ — вне спецификации.

## 13. GLOSSARY

**Records**

- **Consent object** — TTL-запись с автопродлением и мгновенным revoke; четыре типа: `LINK`, `SELF_CONF`, `VOUCH`, `DECLARE` (§2.3).
- **Action** — запись с мгновенным эффектом, без TTL (§2.3).
- **`X_REVOKE`** — паттерн именования: action, отзывающий consent object типа X; подписант совпадает с подписантом объекта (§2.3).
- **`LINK`** — consent object пары ключей; обе подписи (§3.1).
- **`LINK_REVOKE`** — односторонний разрыв: terminирует instance, создаёт poison mark против контрагента (§3.2).
- **`SELF_CONF` / `SELF_CONF_REVOKE`** — само-подтверждение членства в L0 / его отзыв (выход) (§4.2).
- **`VOUCH` / `VOUCH_BATCH` / `VOUCH_REVOKE`** — поручительство члена за кандидата / пакет / отзыв; quorum отзывов = исключение (§4.2).
- **`DECLARE` / `DECLARE_REVOKE`** — голос в C1-quorum / мгновенный отзыв (лёгкое возражение) (§5.2).
- **`L0_GENESIS`** — адрес L0; без привилегий (§4.5).

**Time & state**

- **$t_{sign}$** — подписанное автором время записи; единственный источник времени (§2.4.1).
- **$now()$** — субъективные часы узла (§2.4.1).
- **Future rule / $\Delta$** — $t_{sign} > now+\Delta$: discard с пере-оценкой; в коридоре: deferred (§2.4.2).
- **LWW** — для записей одного назначения действует max $t_{sign}$; замещение при строго большем; равные → меньший $H(\mathrm{record})$ (§2.4.4).
- **Designation** — identity записи для конфликтов: тип + ключевые поля (для парных — включая направление) (§2.4.4).
- **Reconstruction** — нормативное вычисление: сортировка по $(t_{sign}, H)$, последовательное применение (§2.4.6).
- **Stored record set** — хранимое множество записей; аргумент функции состояния (§2.4.8).
- **Re-publish** — повторная публикация живых declarations при изменении membership-статуса (§2.4.9).

**Links**

- **Instance** — текущий `LINK` пары; замещается более свежим (§3.1).
- **Binding** — привязка `LINK_REVOKE` к последнему instance с $t_c \le t_{sign}$ (§3.2.2).
- **Winning revoke** — действующий revoke направления: max $t_{sign}$ на instance (§3.2.3).
- **Mutual revoke** — revoke обоих направлений одной пары; не конфликтуют; обе стороны помечены (§3.2.3).
- **Counter-revoke** — свежая запись того же направления; замещает и отменяет mark подделки в любой момент (§3.2.5).
- **Poison mark** — активна на $[t_b, \min(t_c+T_{life}, t_{relink}))$; ≤1 на пару-направление, ≤2 на пару (§3.2.4).
- **Clamp** — $t_b = \min(t_{sign},\ t_c + T_{life})$: разрыв зажат в базовое окно instance (§3.2.4).
- **$N_x$** — число активных marks против $x$; $N_x \le \deg(x)$ (§3.2).
- **Window / decay** — $W = T_{life}/(1+N_u+N_v)$; $d(\ell)$ — момент распада; необратимость — относительно текущего множества записей (§3.3).
- **Truce** — свежий `LINK` пары: усекает marks обоих направлений, расширяет окна выживающих связей (§3.2, св. 3).
- **GC horizon** — записи пары хранятся до $t_{last}+2T_{life}$; дальше — не влияют ни на что (§2.2.5, §3.4.1).

**L0**

- **Candidate** — ключ с живой `SELF_CONF` (§4.3.1).
- **Materialization** — вхождение кандидата в активный roster (§4.4).
- **Active member** — участник, прошедший rounds (§4.3).
- **Vouch-quorum** — $\lfloor |M|/2 \rfloor + 1$ живых `VOUCH` (§4.3.4a).
- **Cohesion** — $\lfloor |M|/2 \rfloor + 1$ активных связей с активными членами (§4.3.4b).
- **Synchronous rounds** — одновременное удаление нарушителей до фикс-точки; sound, не maximal (§4.3.4).
- **Growth priority** — начальный roster = все кандидаты; присоединение никогда не блокируется (§4.3.3).
- **Squeeze-out** — вытеснение incumbents укрупнёнными порогами; принятая семантика (§4.3.3, §10.16).
- **Cap-30** — отбор кандидатов: vouch count → $t_{sign}$ → pk (§4.3.2).
- **Freshness tie-break** — равные притязания → fresher $t_{sign}$ (§4.3.5).
- **Quench** — $|M_{act}| < 4$: roster пуст, edges отваливаются каскадом (§4.3.6).

**Hierarchy**

- **Isolate** — 0 живых детей; $R_{str} = \varnothing$; привязывается только bootstrap (§5.5, §5.6.2).
- **Vertex** — ≥ 2 живых детей (§5.5).
- **Free group** — 1 живой ребёнок; edge грандфатерится; общие правила (§5.5, §5.6.2).
- **Edge / child / parent / sister** — привязка $X \to H$; X — child, H — parent; другие дети H — sisters (§5.5).
- **C1** — quorum живых declarations (§5.5).
- **C2 (all-pairs)** — corroboration: пары со всеми живыми сёстрами (§5.5).
- **C3** — acyclicity (§5.5).
- **Hold window ($T_{hold}$)** — непрерывное выполнение условий перед активацией (§5.5).
- **Freeze ($T_f$)** — блокировка новых активаций вверх после `L0_GENESIS` и bootstrap; параллелен hold window (§5.5).
- **Bootstrap / S-set** — совместная активация ≥ 2 рёбер к пустой группе; все пары внутри $S$; окно на фиксированном $S$; выбор inclusion-maximal → ранний старт → лексикографический минимум (§5.5).
- **Attach / detach** — присоединение к живой группе / мгновенный отрыв (провал C1 или любой пары — оба edge) (§5.5–5.6).
- **Demotion** — vertex → free group (1 ребёнок) → isolate (0) с отвалом восходящих edges тем же пересчётом (§5.6.2).
- **Grandfathered edge** — edge свободной группы, сохранённый при понижении (§5.6.2).
- **$R_{str}$ / $R_{decl}$** — структурный roster (союз живых детей; задаёт численности) / roster заявлений (не носитель доверия) (§5.3).
- **Level ($L$)** — $1 + \max$ по живым детям; метаданные (§5.6.3).
- **Multi-parenting** — группа — ребёнок любого числа родителей; штатное состояние DAG (§5.6.4).
- **Disjoint count ($U$)** — corroboration только во внешнюю часть контрагента (§5.4.1).
- **$f$-curve / $\gamma$ / $\kappa$ (conspiracy floor)** — пороговая арифметика пар (§5.4.2).

**Network**

- **Neighbor** — узел с активной LINK; транспорт совпадает с графом доверения (§2.2.1).
- **Sync queue** — исходящий буфер ретрансляции (§2.2).
- **Anti-entropy** — периодическая сверка множеств записей; подавляет цензуру и потери (§2.2.3).
- **Mandatory zone** — свои связи и группы; глубже — политика узла (§2.2.4).
- **Relevance** — политика хранения/ретрансляции, не валидности (§2.6.1).
- **Caps / rate-limit** — детерминированные лимиты живых объектов и обновлений на ключ (§2.6).

**Trust**

- **Proof (subtree)** — все дети каждого parent на пути + перекрёстные связи (C2) + численности (§6.1).
- **Spot-check** — опрос $k$ случайных участников rosters о записях, затрагивающих proof; расхождение → reject; SHOULD (§6.3).
- **Trusted set** — транзитивное замыкание родителей L0 верификатора + его политика (§6.2).
- **Inclusion cost** — $\approx t$ взаимных живых связей, рекуррентно $\le T_{life}$ (§1.3).
- **Hijack localization** — сжатие окон в $1+N$; чужие marks нестерираемы; counter-revoke против бэйдейтинга (§7.3).
