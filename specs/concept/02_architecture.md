## 2. Архитектура

<a id="arch-2"></a>

### 2.1 Identity

<a id="arch-2.1"></a>

<a id="arch-2.1.1"></a>

1. Личность — пара ключей $(x, pk)$ (подписывающий секрет $x$ не публикуется; конкретная схема подписи — деталь реализации, [CRYPTO-8](../implementation/02_crypto.md#crypto-8)).

<a id="arch-2.1.2"></a>

2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.

<a id="arch-2.1.3"></a>

3. Один человек может владеть несколькими ключами ([LIM-10.2](10_limitations.md#lim-10.2)); перенос истории протоколом не гарантируется ([DEF-7.3.3](07_defenses.md#def-7.3.3)).

<a id="arch-2.1.4"></a>

4. Отозванный ключ не существует: `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)) делает все записи ключа невалидными от своей $t_{sign}$; записи ключа с большей $t_{sign}$ невалидны по умолчанию — несуществующий ключ не может давать согласие. Правило [ARCH-2.1.2](#arch-2.1.2) не «оживляет» ключ через его собственную запись отзыва.

### 2.2 Сеть без ledger

<a id="arch-2.2"></a>

1. Правило ретрансляции (транспорт = социальный граф) и гарантия транспортной изоляции — [ARCH-2.2.1](../implementation/04_node_transport.md#arch-2.2.1) (implementation).

2. Механика обработки записи на узле — [ARCH-2.2.2-impl](../implementation/04_node_transport.md#arch-2.2.2-impl) (implementation).

3. Anti-entropy: механика и гарантия обнаружения утаивания — [ARCH-2.2.3](../implementation/04_node_transport.md#arch-2.2.3) (implementation).

<a id="arch-2.2.4"></a>

4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).

<a id="arch-2.2.5"></a>

5. **GC horizons (минимум для корректности собственного состояния):** записи пары — до $t_{last} + 2T_{life}$ ($t_{last}$ — позднейшая $t_{sign}$ пары; лемма [LINK-3.4.1](03_links.md#link-3.4.1)); consent objects — до конца эффекта; `KEY_LOSS` — до истечения TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва ([ARCH-2.3.2](#arch-2.3.2)); L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

### 2.3 Записи

<a id="arch-2.3"></a>

Записи канонизируются детерминированной сериализацией ([FMT-2.7](../implementation/01_records_formats.md#fmt-2.7)); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke; два типа: `FRIEND`, `MEMBER_OF`) и **actions** (мгновенный эффект).

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `FRIEND(X, P)` | обе стороны | object, $T_{life}$ | friend instance пары ([LINK-3](03_links.md#link-3)) |
| `FRIEND_REVOKE(X→P, memo?)` | $X$ | action | terminирует instance + poison mark ([LINK-3.2](03_links.md#link-3.2)) |
| `MEMBER_OF(X,G)` | $X$ или подтверждающий | object, $T_{life}$ | членство «X member of G»: L0 и заявления в сообщества ([L0-4](04_l0.md#l0-4), [HIER-5.2](05_hierarchy.md#hier-5.2)) |
| `MEMBER_OF_REVOKE(X,G)` | $X$ или подтверждающий | action | отзыв подтверждения: выход $X$ или отзыв чужого подтверждения ([L0-4.2](04_l0.md#l0-4.2)) |
| `L0_GENESIS(P, descriptor)` | $P$ | action | адрес L0 ([L0-4.5](04_l0.md#l0-4.5)) |
| `KEY_LOSS(memo?)` | сам ключ | action | смерть ключа: инвалидация всех записей ключа ([ARCH-2.3.2](#arch-2.3.2)) |

`MEMBER_OF(X,G)` — единый тип членства, читается «X member of G»: подписант = $X$ — само-членство (для $ID_H$ — заявление о членстве в сообществе); подписант ≠ $X$ — подтверждение члена другим участником (quorum-правило мгновенного исключения для чужих подтверждений — [L0-4.2](04_l0.md#l0-4.2)). Различение сценариев — по типу ID группы: $ID_G$ — базовая группа L0 ([L0-4](04_l0.md#l0-4)); $ID_H$ — сообщество иерархии: живые `MEMBER_OF(P,H)` образуют $R_{decl}(H)$ и голосуют в C1-quorum ([HIER-5.2](05_hierarchy.md#hier-5.2)).

<a id="arch-2.3.1"></a>

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

<a id="arch-2.3.2"></a>

**`KEY_LOSS` — смерть ключа.** Action; подписант — сам ключ (`[self]`, [FMT-2.8](../implementation/01_records_formats.md#fmt-2.8)). Назначение — тип + подписант; экземпляр на ключ один: второй `KEY_LOSS` того же подписанта игнорируется по общим правилам LWW ([ARCH-2.4.4](#arch-2.4.4)). Эффект от $t_{sign}$ записи: все consent-записи ключа — `FRIEND` (в обе стороны) и `MEMBER_OF`, включая живые instance — невалидны; consent-записи ключа с большей $t_{sign}$ невалидны по умолчанию ([ARCH-2.1.4](#arch-2.1.4)). Ключ прекращает существование. `FRIEND` с участием отозванного ключа: instance терминирован; вторая сторона жива, её записи валидны, её перелинковка с новым ключом владельца — обычная связь ([LINK-3.1](03_links.md#link-3.1)). Штрафов нет: `KEY_LOSS` не создаёт poison marks и не влияет на окна/decay — созданные ключом `FRIEND_REVOKE` и метки против ключа сохраняют эффект (отмывание недоступно, [LINK-3.2.9](03_links.md#link-3.2.9)); `break` — это `FRIEND_REVOKE` ([LINK-3.2](03_links.md#link-3.2)), а не `KEY_LOSS`. Roster L0 и C1-кворумы пересчитываются существующими механизмами — мгновенный каскад ([L0-4.3](04_l0.md#l0-4.3), [HIER-5.6](05_hierarchy.md#hier-5.6)). Живость записи `KEY_LOSS` — не меньше TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва; после истечения всех записей ключа его существование ничем не поддерживается; GC-горизонт — [ARCH-2.2.5](#arch-2.2.5).

### 2.4 Время, конфликты, revoke-семантика, детерминизм

<a id="arch-2.4"></a>

<a id="arch-2.4.1"></a>

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.

<a id="arch-2.4.2"></a>

2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и пере-оценивается при повторной доставке (часы могли догнать). $t_{sign} \in (now,\ now+\Delta]$ — хранится и ретранслируется, к состоянию не применяется до догонa часов.

<a id="arch-2.4.3"></a>

3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов ([LINK-3.4.1](03_links.md#link-3.4.1)).

<a id="arch-2.4.4"></a>

4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.

<a id="arch-2.4.5"></a>

5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$: уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$; объекты с большей $t_{sign}$ — свежее согласие, выживают. `X_REVOKE` покрывает consent objects; смерть ключа — отдельный механизм `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)). Специфика `FRIEND_REVOKE` (binding, poison) — [LINK-3.2](03_links.md#link-3.2).

<a id="arch-2.4.6"></a>

6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.

<a id="arch-2.4.7"></a>

7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван ([ARCH-2.4.5](#arch-2.4.5)) ∧ ключ-подписант не отозван ([ARCH-2.3.2](#arch-2.3.2)).

<a id="arch-2.4.8"></a>

8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Транзиторное неравенство хранимых множеств между узлами — норма; сходимость — [ARCH-2.5](../implementation/04_node_transport.md#arch-2.5). Правила игнорирования (детерминированные): неверная подпись; неканоническая форма; $t_{sign} > now+\Delta$; неприменимость (`FRIEND_REVOKE` без bound instance — [LINK-3.2](03_links.md#link-3.2); revoke объекта, которого нет в БД); записи отозванного ключа с $t_{sign} > t_{sign}(\mathrm{KEY\_LOSS})$ ([ARCH-2.3.2](#arch-2.3.2)). Капы [ARCH-2.6.2](#arch-2.6.2) и rate-limit [ARCH-2.6.3](#arch-2.6.3) — правила **отбора и замещения на уровне состояния**, не валидации: «лишние» записи хранятся, но не считаются.

<a id="arch-2.4.9"></a>

9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `MEMBER_OF` (relevance — политика хранения/ретрансляции, не валидности).

### 2.6 Antispam (структурный)

<a id="arch-2.6"></a>

<a id="arch-2.6.1"></a>

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (`MEMBER_OF(P,H)` от ключей $P$ вне живых $R_{str}(H)$ не хранятся; re-publish — [ARCH-2.4.9](#arch-2.4.9)).

<a id="arch-2.6.2"></a>

2. **Капы живых объектов на ключ (уровень состояния):** ≤ 128 живых `MEMBER_OF` на ключ — суммарно: L0-членства и заявления в сообщества (сверх — считаются 128 с наибольшими $t_{sign}$, тай-брейк по $H$); `FRIEND` и `MEMBER_OF_REVOKE` капом не ограничены. Правило подсчёта подтверждений: в кворумы входят только `MEMBER_OF` от текущих членов соответствующего $R_{str}$ (для L0 — [L0-4.3.4-a](04_l0.md#l0-4.3.4-a)); подтверждение от не-члена хранится, не считается.

<a id="arch-2.6.3"></a>

3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.
