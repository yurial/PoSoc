## 2. Архитектура

<a id="arch-2"></a>

### 2.1 Identity

<a id="arch-2.1"></a>

<a id="arch-2.1.1"></a>

1. Личность — пара ключей $(x, pk)$, Ed25519 ([CRYPTO-8](../implementation/02_crypto.md#crypto-8)). Секрет не публикуется.

<a id="arch-2.1.2"></a>

2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.

<a id="arch-2.1.3"></a>

3. Один человек может владеть несколькими ключами ([LIM-10.2](10_limitations.md#lim-10.2)); перенос истории протоколом не гарантируется ([DEF-7.3.3](07_defenses.md#def-7.3.3)).

### 2.2 Сеть без ledger

<a id="arch-2.2"></a>

**Объекты узла:** БД состояния (живые записи + ретроспективный буфер), sync queue.

<a id="arch-2.2.1"></a>

1. **Транспорт = социальный граф.** Запись ретранслируется только узлам с активной LINK. Компонент связности — изолированная вселенная данных: записи человеческого компонента физически не достигают бот-кластеров (двойная изоляция). Свежий ключ без связей не получает трафика; установление LINK включает слив состояния.

<a id="arch-2.2.2"></a>

2. **Обработка записи:** проверка (подписи, каноническая форма, применимость, [ARCH-2.4.8](#arch-2.4.8)) → применение к БД → постановка в sync queue → рассылка соседям.

<a id="arch-2.2.3"></a>

3. **Anti-entropy.** Периодическая сверка множеств записей с каждым соседом (реконсиляция по диапазонам времени и хешам); расхождения подтягиваются. Утаивание записей соседом обнаруживается сверкой через других соседей; риск единственного моста — [LIM-10.9](10_limitations.md#lim-10.9).

<a id="arch-2.2.4"></a>

4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).

<a id="arch-2.2.5"></a>

5. **GC horizons (минимум для корректности собственного состояния):** записи пары — до $t_{last} + 2T_{life}$ ($t_{last}$ — позднейшая $t_{sign}$ пары; лемма [LINK-3.4.1](03_links.md#link-3.4.1)); consent objects — до конца эффекта; L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

### 2.3 Записи

<a id="arch-2.3"></a>

Канонический CBOR ([FMT-2.7](../implementation/01_records_formats.md#fmt-2.7)); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke) и **actions** (мгновенный эффект).

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `LINK(u,v)` | обе стороны | object, $T_{life}$ | link instance пары ([LINK-3](03_links.md#link-3)) |
| `LINK_REVOKE(u→v, memo?)` | $u$ | action | terminирует instance + poison mark ([LINK-3.2](03_links.md#link-3.2)) |
| `SELF_CONF(P,G)` | $P$ | object, $T_{life}$ | само-подтверждение членства в L0 ([L0-4](04_l0.md#l0-4)) |
| `SELF_CONF_REVOKE(P,G)` | $P$ | action | отзыв → выход из L0 ([L0-4.2](04_l0.md#l0-4.2)) |
| `VOUCH(Q,P,G)` | $Q$ | object, $T_{life}$ | поручительство за $P$ ([L0-4](04_l0.md#l0-4)) |
| `VOUCH_BATCH(Q,G,[P…])` | $Q$ | object (пакет) | набор vouches ([L0-4](04_l0.md#l0-4)) |
| `VOUCH_REVOKE(Q,P,G)` | $Q$ | action | отзыв vouch ([L0-4.2](04_l0.md#l0-4.2)) |
| `DECLARE(P,H)` | $P$ | object, $T_{life}$ | голос в C1-quorum ([HIER-5.2](05_hierarchy.md#hier-5.2)) |
| `DECLARE_REVOKE(P,H)` | $P$ | action | отзыв declaration ([HIER-5.2](05_hierarchy.md#hier-5.2)) |
| `L0_GENESIS(P, descriptor)` | $P$ | action | адрес L0 ([L0-4.5](04_l0.md#l0-4.5)) |

<a id="arch-2.3.1"></a>

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

### 2.4 Время, конфликты, revoke-семантика, детерминизм

<a id="arch-2.4"></a>

<a id="arch-2.4.1"></a>

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.

<a id="arch-2.4.2"></a>

2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и пере-оценивается при повторной доставке (часы могли догнать). $t_{sign} \in (now,\ now+\Delta]$ — хранится и ретранслируется, к состоянию не применяется до догонa часов.

<a id="arch-2.4.3"></a>

3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов ([LINK-3.4.1](03_links.md#link-3.4.1)).

<a id="arch-2.4.4"></a>

4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.

<a id="arch-2.4.5"></a>

5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$: уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$; объекты с большей $t_{sign}$ — свежее согласие, выживают. Специфика `LINK_REVOKE` (binding, poison) — [LINK-3.2](03_links.md#link-3.2).

<a id="arch-2.4.6"></a>

6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.

<a id="arch-2.4.7"></a>

7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван ([ARCH-2.4.5](#arch-2.4.5)).

<a id="arch-2.4.8"></a>

8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Транзиторное неравенство хранимых множеств между узлами — норма; сходимость — [ARCH-2.5](#arch-2.5). Правила игнорирования (детерминированные): неверная подпись; неканоническая форма; $t_{sign} > now+\Delta$; неприменимость (`LINK_REVOKE` без bound instance — [LINK-3.2](03_links.md#link-3.2); revoke объекта, которого нет в БД). Капы [ARCH-2.6.2](#arch-2.6.2) и rate-limit [ARCH-2.6.3](#arch-2.6.3) — правила **отбора и замещения на уровне состояния**, не валидации: «лишние» записи хранятся, но не считаются.

<a id="arch-2.4.9"></a>

9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `DECLARE` (relevance — политика хранения/ретрансляции, не валидности).

### 2.5 Синхронизация и сходимость

<a id="arch-2.5"></a>

Gossip при появлении записи + anti-entropy по расписанию. Согласованность — в пределе; в моменте — субъективные виды. Потребитель доверия всегда читает текущее состояние. Цензура соседа подавляет доставку, но не искажает семантику: задержанная запись применяется со своей $t_{sign}$.

### 2.6 Antispam (структурный)

<a id="arch-2.6"></a>

<a id="arch-2.6.1"></a>

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (declarations от ключей вне живых $R_{str}$ не хранятся; re-publish — [ARCH-2.4.9](#arch-2.4.9)).

<a id="arch-2.6.2"></a>

2. **Капы живых объектов на ключ (уровень состояния):** ≤ 16 `SELF_CONF`; ≤ 32 `DECLARE` (сверх — считаются 32 с наибольшими $t_{sign}$, тай-брейк по $H$); `VOUCH` считается только от активных членов (правило подсчёта: vouch от не-члена хранится, не считается); `LINK` капом не ограничен (стоимость встроена в подпись контрагента).

<a id="arch-2.6.3"></a>

3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.
