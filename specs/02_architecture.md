## 2. Архитектура

### 2.1 Identity

1. Личность — пара ключей $(x, pk)$, Ed25519 (§8). Секрет не публикуется.
2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.
3. Один человек может владеть несколькими ключами (§10.2); перенос истории протоколом не гарантируется (§7.3.3).

### 2.2 Сеть без ledger

**Объекты узла:** БД состояния (живые записи + ретроспективный буфер), sync queue.

1. **Транспорт = социальный граф.** Запись ретранслируется только узлам с активной LINK. Компонент связности — изолированная вселенная данных: записи человеческого компонента физически не достигают бот-кластеров (двойная изоляция). Свежий ключ без связей не получает трафика; установление LINK включает слив состояния.
2. **Обработка записи:** проверка (подписи, каноническая форма, применимость, §2.4.8) → применение к БД → постановка в sync queue → рассылка соседям.
3. **Anti-entropy.** Периодическая сверка множеств записей с каждым соседом (реконсиляция по диапазонам времени и хешам); расхождения подтягиваются. Утаивание записей соседом обнаруживается сверкой через других соседей; риск единственного моста — §10.9.
4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).
5. **GC horizons (минимум для корректности собственного состояния):** записи пары — до $t_{last} + 2T_{life}$ ($t_{last}$ — позднейшая $t_{sign}$ пары; лемма §3.4.1); consent objects — до конца эффекта; L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

### 2.3 Записи

Канонический CBOR (§2.7); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke) и **actions** (мгновенный эффект).

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `LINK(u,v)` | обе стороны | object, $T_{life}$ | link instance пары (§3) |
| `LINK_REVOKE(u→v, memo?)` | $u$ | action | terminирует instance + poison mark (§3.2) |
| `SELF_CONF(P,G)` | $P$ | object, $T_{life}$ | само-подтверждение членства в L0 (§4) |
| `SELF_CONF_REVOKE(P,G)` | $P$ | action | отзыв → выход из L0 (§4.2) |
| `VOUCH(Q,P,G)` | $Q$ | object, $T_{life}$ | поручительство за $P$ (§4) |
| `VOUCH_BATCH(Q,G,[P…])` | $Q$ | object (пакет) | набор vouches (§4) |
| `VOUCH_REVOKE(Q,P,G)` | $Q$ | action | отзыв vouch (§4.2) |
| `DECLARE(P,H)` | $P$ | object, $T_{life}$ | голос в C1-quorum (§5.2) |
| `DECLARE_REVOKE(P,H)` | $P$ | action | отзыв declaration (§5.2) |
| `L0_GENESIS(P, descriptor)` | $P$ | action | адрес L0 (§4.5) |

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

### 2.4 Время, конфликты, revoke-семантика, детерминизм

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.
2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и пере-оценивается при повторной доставке (часы могли догнать). $t_{sign} \in (now,\ now+\Delta]$ — хранится и ретранслируется, к состоянию не применяется до догонa часов.
3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов (§3.4.1).
4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.
5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$: уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$; объекты с большей $t_{sign}$ — свежее согласие, выживают. Специфика `LINK_REVOKE` (binding, poison) — §3.2.
6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.
7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван (§2.4.5).
8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Транзиторное неравенство хранимых множеств между узлами — норма; сходимость — §2.5. Правила игнорирования (детерминированные): неверная подпись; неканоническая форма; $t_{sign} > now+\Delta$; неприменимость (`LINK_REVOKE` без bound instance — §3.2; revoke объекта, которого нет в БД). Капы §2.6.2 и rate-limit §2.6.3 — правила **отбора и замещения на уровне состояния**, не валидации: «лишние» записи хранятся, но не считаются.
9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `DECLARE` (relevance — политика хранения/ретрансляции, не валидности).

### 2.5 Синхронизация и сходимость

Gossip при появлении записи + anti-entropy по расписанию. Согласованность — в пределе; в моменте — субъективные виды. Потребитель доверия всегда читает текущее состояние. Цензура соседа подавляет доставку, но не искажает семантику: задержанная запись применяется со своей $t_{sign}$.

### 2.6 Antispam (структурный)

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (declarations от ключей вне живых $R_{str}$ не хранятся; re-publish — §2.4.9).
2. **Капы живых объектов на ключ (уровень состояния):** ≤ 16 `SELF_CONF`; ≤ 32 `DECLARE` (сверх — считаются 32 с наибольшими $t_{sign}$, тай-брейк по $H$); `VOUCH` считается только от активных членов (правило подсчёта: vouch от не-члена хранится, не считается); `LINK` капом не ограничен (стоимость встроена в подпись контрагента).
3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.

### 2.7 Канонизация

Канонический CBOR (ключи отсортированы); пары ключей лексикографически; самосвязи запрещены; $H$ — BLAKE3; округления порогов — $\lfloor x + 10^{-9} \rfloor$.

### 2.8 Record formats (норматив)

Record = `{type, t_sign, payload, sigs}`; sigs — массив `{pk, sig}`, **отсортированный по pk**. Signing payload = канонический CBOR `{type, t_sign, payload}` — каждый подписант подписывает одни и те же байты. Идентичность записи = $H(\mathrm{record})$ (полные канонические байты); дедупликация по содержимому.

| type | payload | sigs |
|---|---|---|
| `LINK` | `{u: pk, v: pk}` ($u < v$) | `[u, v]` |
| `LINK_REVOKE` | `{from: pk, to: pk, memo?: bstr ≤ 256}` | `[from]` |
| `SELF_CONF` / `SELF_CONF_REVOKE` | `{group: ID_G, member: pk}` | `[member]` |
| `VOUCH` / `VOUCH_REVOKE` | `{group: ID_G, voucher: pk, member: pk}` | `[voucher]` |
| `VOUCH_BATCH` | `{group: ID_G, voucher: pk, members: [pk; ≤30]}` | `[voucher]` |
| `DECLARE` / `DECLARE_REVOKE` | `{group: ID_H, declarant: pk}` | `[declarant]` |
| `L0_GENESIS` | `{descriptor: tstr ≤ 128, initiator: pk}` | `[initiator]` |

Идентификаторы: $ID_G = H(\texttt{"L0"} \Vert \text{descriptor} \Vert pk_{initiator} \Vert t_{sign})$; $ID_H = H(\texttt{"GROUP"} \Vert \text{descriptor} \Vert pk_{founder})$, founder — pk первой (по $t_{sign}$) `DECLARE` (техническая роль без привилегий). Доменное разделение BLAKE3 — по тегам типов; tie-break $H(\mathrm{record})$ — от полных канонических байтов.
